# My Writing

## 핵심

- 이 스킬은 PR과 Notion 초안을 쓰고 고치는 말투를 다룬다.
- 정답 목록이 아니라, 사실을 어떤 순서와 밀도로 접어 넣는지 다룬다.
- 기본 언어는 한국어다. 사용자가 다른 언어를 명시하면 같은 직설과 밀도를 유지하고, 억지로 한국어식 어미로 바꾸지 않는다.
- 목표는 예쁜 문장이 아니라 현재 사실을 가장 짧고 정확하게 옮기는 것이다.
- 모호하면 꾸미지 말고 좁게 쓴다. 테스트, 수치, 링크, 위험, 의도는 사실이 있을 때만 쓴다.

## 우선순위

1. 지금 확인되는 사실
2. 사용자가 직접 쓴 말과 형식
3. 현재 저장소 템플릿 또는 현재 Notion 구조
4. 개인적인 말투

- 템플릿은 구조로만 따른다.
- 필수 구조는 보존한다. 삭제해도 되는 선택 섹션은 근거가 없으면 제거하고, 삭제할 수 없는 섹션에는 filler를 만들지 않는다.
- 템플릿 문구를 말투로 착각하지 않는다.

## 라우팅

- PR, 변경 요약, 리뷰 요청, 배포/마이그레이션 안내가 목적이면 PR 모드
- 메모, 결정, 조사, 회의 기록, how-to가 목적이면 Notion 모드
- 둘 다 걸리면 사용자의 요청 형식을 우선하고, 템플릿이 있으면 그 구조를 따른다

## 공통 말투

- 운영 메모처럼 시작하고, 이해에 필요한 만큼만 설명한다.
- 짧은 문장, 짧은 불릿, 낮은 장식성
- 사실이 먼저, 해석은 그다음
- 추상어보다 구체 명사
- 길게 설명해야 할 때도 결론부터 간다
- 과장된 안전장치 문구, 마케팅 톤, 컨설팅식 정리문, 이모지, 장식성 제목은 쓰지 않는다
- 사용자의 압축과 리듬을 따라가되 오타나 공백 습관을 일부러 복제하지는 않는다

## 작성 절차

1. 사실 수집
   - 변경된 파일, 동작, 쿼리, 화면, 절차, 로그, 선택지, 남은 불확실성을 적는다
   - PR이면 실제 git 변경과 저장소 PR 템플릿을 먼저 본다
   - 원격 게시나 원격 수정은 명시 요청이 있을 때만 한다
2. 모드 선택
   - PR이면 tiny / standard / evidence-heavy / risky / infra 중 하나를 고른다
   - Notion이면 short note / problem-solution / design-decision / investigation-postmortem / how-to / meeting-action 중 하나를 고른다
3. 초안 작성
   - 가장 중요한 사실을 먼저 쓴다
   - 보이는 사실만 쓴다
   - 빈약하면 넓게 말하지 말고 짧게 유지한다
4. 근접 예시 비교
   - 아래 예시 중 가장 가까운 것과 비교한다
   - 불일치한 문장만 고친다
   - 내부 분석은 드러내지 않는다
5. 최종 출력
   - 요청된 산출물만 내보낸다
   - 설명, 메타코멘트, 스타일 해설은 붙이지 않는다

## PR 모드

- 제목은 전보체처럼 짧게 쓴다
- 문장보다 fragment를 선호한다
- prefix는 저장소나 브랜치 관례가 맞을 때만 쓴다
- 본문은 불릿 중심이다
- 보통은 1~4개 불릿이면 충분하다
- 작은 PR은 짧게, 큰 PR은 근거를 붙여서 길어진다
- 구체 기술 명사(file, class, method, endpoint, query, field, table, migration, image, batch 등)를 쓴다
- 변경에 실질적 영향이 있으면 리뷰어에게 하나의 핵심 확인만 요청한다. 작은 수정은 생략할 수 있다
- 위험한 변경이면 위험을 직접 적고, 배포/마이그레이션/모니터링이 있으면 짧게 분리한다
- 템플릿이 삭제를 허용하는 선택 섹션은 제거하고, 보존이 필요한 섹션만 비워둘 수 있다
- 변경이 작으면 스크린샷, 테스트, 배포 계획을 억지로 채우지 않는다
- 저장소 안의 PR이라면 실제 git diff와 PR 템플릿을 먼저 확인한다
- 원격 발행, 원격 수정, 멀티스텝 배포를 임의로 진행하지 않는다

### PR 하위 모드

- tiny: 한 줄 수정, 롤백, 좁은 핫픽스
- standard: 대부분의 기능/수정
- evidence-heavy: UI, API, SQL, 스키마, 비교 화면, 출력 예시가 핵심
- risky: migration, 정책, 상태 변경, 데이터 영향
- infra: 배치, CI, 런너, 배포, 도구 변경

### PR 문장 습관

- `변경하였습니다`, `추가하였습니다`, `제거하였습니다`, `이관하였습니다`, `통합하였습니다`를 자주 쓴다
- `기존 동작과 달라진 부분이 있는지 확인 부탁드립니다` 같은 짧은 리뷰어 질문을 쓴다
- 근거가 없으면 `문제가 없어 보입니다`처럼 단정하지 않는다
- 범용 칭찬이나 장점 나열은 쓰지 않는다

## Notion 모드

- 내부 작업 메모처럼 쓴다
- PR보다 조금 더 맥락, 대안, 미확정 항목을 담아도 된다
- 짧은 메모에는 섹션을 강제하지 않는다. 긴 문서는 실제 결정과 근거가 있을 때만 확장한다
- 그래도 에세이는 아니다
- 기능적 제목과 짧은 섹션이 잘 맞는다
- 문제 -> 근거 -> 결정/액션 흐름을 유지한다
- 정리가 안 된 부분은 억지로 닫지 말고 질문으로 남긴다

### Notion 하위 모드

- short note: 짧은 관찰, 기억할 점, 작은 결론
- problem-solution: 문제를 압축한 추천
- design-decision: 옵션과 tradeoff, 선택
- investigation-postmortem: 사건, 로그, 원인 후보, 조치
- how-to: 반복 가능한 절차
- meeting-action: 회의 기록, 결정, 담당, 다음 작업

### Notion 문장 습관

- 기능적인 제목을 쓴다: `문제`, `배경`, `결론`, `다음 작업`, `Action Item`
- 불릿이 기본이다
- 필요하면 체크박스, 날짜, 화자 표기, 표를 쓴다
- `확인 필요`, `미정`, `추정` 같은 실용적 hedging을 쓴다
- 결론은 운영적으로 끝낸다: 무엇을 할지, 무엇을 확인할지, 무엇이 열려 있는지
- 요약을 길게 꾸미지 않는다

## 예외와 금지

- 사실이 없는데 테스트, 수치, 링크, 위험을 만들어 넣지 않는다
- 과도한 양쪽 균형, 중립적 말끝, 컨설턴트식 마무리를 쓰지 않는다
- 장식용 이모지, 과장된 제목, 긴 서론, 반복 요약을 쓰지 않는다
- 작은 변경에 큰 체크리스트를 붙이지 않는다
- 템플릿이 비어 있으면 억지로 채우지 않는다
- 중요한 사실이 빠졌으면 넓게 추정하지 말고 짧게 유지한다
- 의도가 보이지 않으면 의도를 발명하지 않는다
- PR에서는 현재 저장소 맥락을 넘어선 원격 조작을 하지 않는다

## 비교 기준

- PR은 변경과 리뷰 포인트가 핵심이다
- Notion은 문제, 근거, 결정, 다음 작업이 핵심이다
- PR은 더 압축되고, Notion은 조금 더 작업 메모에 가깝다
- 둘 다 공통적으로 공손한 장식보다 구체 사실이 우선이다

## 임베디드 데모

예시는 문장의 모양만 참고한다. 예시의 사실이나 표현을 새 글에 복사하지 않는다.

### PR 1 — tiny

**상황:** 존재하지 않는 항목을 수정할 때 오류 처리가 빠져 있음  
**제목:** 존재하지 않는 항목 수정 오류 처리  
**본문:**
- 존재하지 않는 항목을 수정할 때 오류 응답을 반환하도록 변경하였습니다.

### PR 2 — standard

**상황:** 클라이언트에서 하던 마스킹을 서버에서 처리하도록 바꿈  
**제목:** 마스킹 처리 서버 이관  
**본문:**
- 마스킹 로직을 서버로 옮기고 클라이언트 쪽 처리는 제거하였습니다.
- 화면 표시가 기존과 같은지 확인 부탁드립니다.

### PR 3 — evidence-heavy

**상황:** 같은 목록과 카운트를 주던 두 경로를 하나의 파라미터로 합침  
**제목:** 중복 조회 API 통합  
**본문:**
- 기존에는 두 엔드포인트에서 같은 목록과 카운트를 각각 응답하고 있었습니다.
- 하나의 쿼리 파라미터로 조회 대상을 구분하도록 통합하였습니다.
- 기존 호출 흐름에 영향 없는지 확인 부탁드립니다.

### PR 4 — risky

**상황:** 배포 중 기존 데이터와 신규 데이터가 함께 조회되고, 문제 시 이전 단계로 돌아갈 수 있어야 하는 스키마 변경  
**제목:** 신규 스키마 전환 단계 분리  
**본문:**
- 기존 데이터와 신규 데이터를 함께 읽을 수 있도록 전환 단계를 분리하였습니다.
- 마이그레이션 후 두 데이터가 함께 조회되는지 확인하겠습니다.
- 문제가 있으면 이전 단계로 되돌릴 수 있도록 배포 순서를 나눴습니다.

### Notion 1 — short note

**상황:** 리스트가 커질수록 응답이 느려짐  
**출력:**
- 목록을 매번 전부 읽고 있어서 느려짐
- 필요한 항목만 가져오는 방식으로 변경 필요

### Notion 2 — problem-solution

**상황:** 두 단계 저장이 따로 성공/실패할 수 있어 정합성이 깨짐  
**출력**

## 문제

- 앞 단계만 저장되고 뒤 단계가 실패할 수 있습니다.

## 판단

- 저장 시점에 묶거나, 커밋 뒤 후속 작업으로 분리하는 편이 안전합니다.

## 다음 작업

- 둘 중 어느 쪽이 현재 구조에 맞는지 확인합니다.

### Notion 3 — investigation

**상황:** 배경 작업이 상태 확인 실패 뒤 반복 재시작됨  
**출력**

## 조사

- 주기적으로 상태가 끊기면서 재시작이 반복되었습니다.
- 로그 시점과 재시작 시점을 맞춰 보니 상태 확인 쪽이 후보였습니다.

## 조치

- 상태 확인 주기와 실제 처리 주기를 분리해 다시 봅니다.

## 남은 질문

- 재시작이 처리 지연 때문인지, 확인 조건 때문인지 더 봐야 합니다.

### Notion 4 — design-decision

**상황:** 회의에서 두 방식 중 하나를 골라야 함  
**출력**

## 결정

- 구현이 단순한 쪽을 먼저 갑니다.
- 예외가 늘어나는 방식은 뒤로 미룹니다.

## 다음 작업

- 검증 범위와 확인 포인트를 정리합니다.

## 리라이트 쌍

**일반형:** 이 변경은 best practices를 적용해 전체적으로 더 robust하게 만듭니다.

**자연형**
